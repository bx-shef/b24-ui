# Сайт документации Bitrix24 UI в Docker

Сайт из `docs/` (Nuxt 4 + Nitro-сервер: серверные маршруты, MCP-сервер `/mcp/`, `llms.txt`, `raw/*.md`)
собирается в образ `ghcr.io/bx-shef/b24-ui-docs` и крутится на своём сервере за общим `nginx-proxy` с TLS.
Схема та же, что у остальных сайтов bx-shef: GitHub Actions публикует образ на каждый push в `main`,
общий Watchtower на сервере подхватывает новый `:latest`.

| Файл | Зачем |
|---|---|
| `Dockerfile` | сборка: библиотека, затем `docs`; финальный образ `node:24-slim`, `USER node`, порт 3000, healthcheck |
| `docker-compose.prod.yml` | сервис за прокси в сети `proxy-net` (`VIRTUAL_HOST`, `LETSENCRYPT_HOST`), метка Watchtower |
| `proxy.compose.yml`, `proxy-errorlog.conf` | общий прокси — только если его на сервере ещё нет; журнал без IP и строки запроса |
| `proxy-limits.conf`, `mcp-location.conf` | лимит запросов к `/mcp/` (30 в минуту с адреса, всплеск 20, сверх — 429); `install.sh` кладёт их в прокси |
| `watchtower.compose.yml` | общий Watchtower — только если его на сервере ещё нет |
| `install.sh`, `Makefile`, `.env.example` | установка и обновление на сервере; в `.env.example` — и ключ чата (`NUXT_DEEPSEEK_API_KEY`) |
| `../../.github/workflows/docs-image.yml` | сборка, дымовая проверка и публикация образа |

## Адреса сайта: сборка и рантайм

Домен **вшивается в образ при сборке**. Проверено на собранном сайте: `NUXT_PUBLIC_SITE_URL`,
`NUXT_PUBLIC_CANONICAL_URL` и `NUXT_PUBLIC_GIT_URL` попадают в `runtimeConfig.public` и в рантайме
переопределяются, но сайт при сборке пререндерит около 400 страниц (HTML, `sitemap.md`, `.well-known/*`,
`raw/*.md` — с адресом в canonical и ссылках), и они остаются с адресом сборки. Рантайм-переопределение
действует только на страницы, которые рендерит сервер (ответы MCP, часть маршрутов) — получился бы сайт
с двумя адресами. Поэтому в `docker-compose.prod.yml` этих переменных нет, а адрес задаётся при сборке:

- `SITE_URL` — build-arg образа (`https://домен`, без слэша на конце); `CANONICAL_URL` по умолчанию равен ему;
- в GitHub Actions — `DOCS_SITE_URL` (Settings → Secrets and variables → Actions → вкладка Variables или
  Secrets; если заданы обе, берётся переменная) или поле `site_url` при ручном запуске workflow; пусто —
  плейсхолдер `https://docs.example.com`, образ собирается, но не публикуется;
- `NUXT_PUBLIC_BASE_URL` (подкаталог) в образе пуст: сайт стоит в корне домена, как нужно за `nginx-proxy`.

Сменили домен — задайте `DOCS_SITE_URL`, запустите workflow «Docs image» (Run workflow), на сервере
поменяйте `DOMAIN` в `.env` и выполните `make prod-redeploy`.

> Домен ещё не выбран владельцем (bx-shef/b24-ui#9): пока везде плейсхолдер `docs.example.com`.
> `install.sh` и `make doctor` с плейсхолдером не работают — это защита от выпуска сертификата на чужой домен.

## Чат «Спросить AI»

На сайте есть чат-помощник по документации: кнопка «Спросить AI» в шапке, пункт в поиске (⌘K) и кнопка
«Объяснить с AI» на страницах документации. Модель — DeepSeek (OpenAI-совместимый API
`https://api.deepseek.com`), документацию она читает теми же инструментами, что и MCP-сервер сайта (`/mcp/`).

- **Включение.** Ключ API DeepSeek кладётся в `.env` на сервере: `NUXT_DEEPSEEK_API_KEY=…`, затем `make prod-up`
  (контейнер пересоздаётся). Модель — `NUXT_DEEPSEEK_MODEL` (`deepseek-chat` по умолчанию, можно `deepseek-reasoner`).
  Ключ не входит ни в репозиторий, ни в образ; клиенту он не отдаётся.
- **Без ключа** (значение по умолчанию) чата на сайте нет: кнопок нет, `POST /api/ai` отвечает 404, к провайдеру
  запросы не уходят. Страницы предрендерены без ключа, поэтому браузер спрашивает у сервера `GET /api/ai/status` —
  пересборка образа для включения чата не нужна.
- **Защита.** Маршрут публичный, поэтому сервер ограничивает частоту: 20 запросов за 10 минут с одного адреса,
  400 за 10 минут и 2000 за сутки на весь чат (ответ 429 с `Retry-After` и понятным текстом). Адрес IPv6 считается по сети /64.
  Размер: не больше 40 сообщений в беседе, 2000 знаков в вопросе, 2 МБ тела (предел действует на само чтение, chunked не
  обходит); пустые сообщения — 400; результат инструмента, который читает модель, обрезается до 14 000 знаков с пометкой.
  Счётчики живут в памяти процесса и обнуляются при перезапуске контейнера.
  **Лимит по адресу работает только когда сайт стоит за `nginx-proxy`, а перед ним нет CDN или другого прокси**:
  адрес клиента — последняя запись `X-Forwarded-For`, которую дописывает `nginx-proxy`. За CDN там окажется адрес CDN
  (все посетители в одной ячейке), без прокси заголовок подделывает клиент и лимит по адресу не защищает;
  общие потолки (окно и сутки) действуют в любом случае.
- **Ключ не задают при сборке образа.** Ключ — только в `.env` на сервере. Переменная `NUXT_DEEPSEEK_API_KEY` в окружении
  сборки (`docker build`, CI) включит флаг `runtimeConfig.public.aiChat` в предрендеренных страницах, хотя ключа в образе нет.
- **Расход.** Каждый вопрос — один или несколько запросов к DeepSeek (поиск по документации — отдельные шаги).
  Следите за балансом на platform.deepseek.com; закончились средства — чат отвечает «временно недоступен», сайт работает.
- **Журнал.** При ошибке провайдера в журнал контейнера пишутся только имя ошибки и HTTP-статус, без текста бесед и ключа.
- **Запрос на разработку.** Если в документации нет ответа, нужного компонента или возможности, либо описана ошибка
  в библиотеке, чат честно говорит об этом и предлагает запрос на разработку: инструмент `request_development`
  (`docs/server/utils/chatDevRequest.ts`) ничего не отправляет, а окно показывает карточку «Запрос на разработку»
  с черновиком текста и кнопками «Скопировать текст» и «Открыть форму». Форма — `https://cowork.bx-shef.by/?type=dev&product=b24-ui#start`;
  адрес зашит константой в `docs/shared/devRequest.ts`, модель его не задаёт. Отправляет запрос сам посетитель.
  В Метрику уходят цели `Dev Request Suggested` и `Dev Request Form Opened` с видом запроса (`kind`), без текста.
- **Приватность.** Беседа хранится в браузере посетителя (localStorage), на сервере не сохраняется; тексты вопросов
  уходят провайдеру (DeepSeek).

## Счётчик Яндекс Метрики

Счётчик подключается клиентским плагином `docs/app/plugins/yandex-metrika.client.ts`. Номер — `runtimeConfig.public.yandexMetrikaId`
(`NUXT_PUBLIC_YANDEX_METRIKA_ID`), только цифры; пусто или что-то кроме цифр — ни баннера согласия, ни скрипта `mc.yandex.ru`, ни запросов.
Вебвизор выключен (он записывает ввод в поля поиска и чата). Просмотры SPA и цели (`reachGoal`: поиск, чат, тема, песочница,
действия страницы) уходят только при заданном номере и после согласия на аналитику; текст сообщений чата не отправляется,
у поиска уходит только длина запроса.

**Согласие.** При заданном номере сайт показывает баннер согласия на cookie — `docs/public/cookie-consent.js`, общий для сайтов
линейки (побайтная копия из bx-shef/toolsai, `site/landing/cookie-consent.js`; правится только в источнике). Политика — https://offer.bx-shef.by/privacy.
`tag.js` Метрики, инициализация и просмотры запускаются после «Принять все» (или «Сохранить» с включённой аналитикой), а если
согласие дано раньше — сразу при загрузке страницы. Пока выбора нет и после отказа запросов к `mc.yandex.ru` нет, цели не копятся
в очереди. Выбор хранится в cookie `cookie_consent`; изменить его можно ссылкой с атрибутом `data-cookie-settings`.

**Номер вшивается при сборке, не при запуске.** Страницы предрендерены, и их `runtimeConfig` остаётся с номером сборки
(как адрес сайта, «Адреса сайта»). Поэтому:

- в GitHub Actions — `YANDEX_METRIKA_ID` (Settings → Secrets and variables → Actions → вкладка Variables или Secrets),
  `docs-image.yml` передаёт её build-arg'ом `YANDEX_METRIKA_ID`; пусто — образ без счётчика;
- при ручной сборке: `docker build ... --build-arg YANDEX_METRIKA_ID=12345678`;
- смена номера — пересборка образа (workflow «Docs image», Run workflow — поля для номера там нет, берётся переменная репозитория). `NUXT_PUBLIC_YANDEX_METRIKA_ID` в `.env` сервера
  пробрасывается в контейнер, но действует лишь на страницы, которые рендерит сам сервер, — полагаться на него одного нельзя.

Content-Security-Policy на сайте не задана, добавлять `mc.yandex.ru` не требуется; появится CSP — разрешить
`mc.yandex.ru`, `mc.yandex.com`, `yastatic.net` (script-src, img-src, connect-src, frame-src) и свой `/cookie-consent.js` (script-src 'self').

## Сервер

Нужно: Linux с Docker и `docker compose` v2, A-запись домена на сервер, порты 80 и 443 (если прокси ещё нет).

Одна команда (первая установка и каждое обновление файлов):

```bash
git clone https://github.com/bx-shef/b24-ui.git
DOMAIN=<домен> EMAIL=<почта для Let's Encrypt> sudo -E bash b24-ui/deploy/docs/install.sh
```

Скрипт: проверяет Docker, кладёт файлы в `/home/bitrix/b24-ui-docs` (`B24_DIR=` — другой каталог; `B24_PROXY=` — имя контейнера, если `nginx-proxy` на сервере несколько), пишет `.env`,
находит работающий `nginx-proxy` (не трогает его; если прокси нет и порты свободны — ставит `proxy.compose.yml`),
подключает прокси к сети `proxy-net` (если он вне её), включает лимит `/mcp/` (`nginx -t` и reload; не прошёл — откат
и предупреждение), скачивает образ, поднимает контейнер и ждёт ответа `/llms.txt`. Сертификат выпускается 1–2 минуты после того,
как DNS указывает на сервер.

Если пакет `ghcr.io/bx-shef/b24-ui-docs` приватный, до установки войдите **от того же пользователя, под которым
идёт установка (root при `sudo`)**: `sudo docker login ghcr.io -u <логин GitHub>` (пароль — classic PAT только
с `read:packages`).

Контейнер ограничен: 1 ГБ памяти, 1 CPU, 200 процессов, без capabilities и с `no-new-privileges`; код образа
только читается, база контента (`NUXT_CONTENT_DATABASE_FILENAME`) лежит в `/data` и пересоздаётся при старте.
Журнал прокси не содержит IP и строки запроса. Лимит `/mcp/`: у прокси из `proxy.compose.yml` зона
смонтирована (`proxy-limits.conf`) и переживает пересоздание. В чужой общий прокси оба файла кладутся
`docker cp`: после пересоздания такого прокси повторите `install.sh`. Если у домена в прокси уже есть свой
`vhost.d/<домен>_location`, `install.sh` его не трогает и пишет, какие строки добавить вручную.

### Обновление

- **Само.** Общий Watchtower (проверка раз в 5 минут) подхватывает новый `:latest` по метке
  `com.centurylinklabs.watchtower.enable=true`. Если Watchtower на хосте нет: в `/home/bitrix/watchtower/.env`
  — `GHCR_USER`, `GHCR_TOKEN`, `WATCHTOWER_API_VERSION=1.44`, затем `make shared-watchtower`.
- **Сразу:** `cd /home/bitrix/b24-ui-docs && make prod-redeploy` (под пользователем с доступом к Docker; для
  приватного пакета — после `docker login ghcr.io` от него же).
- **Файлы установки** (compose, Makefile) — `git pull` в клоне и та же команда `install.sh`.
- **Закрепить версию:** `IMAGE_TAG=sha-<коммит>` в `.env`, `make prod-up`.

Прочее: `make help` (список), `make doctor` (сеть, прокси, Watchtower, `.env`), `make health`, `make logs`.

## Сборка образа

Контекст — корень репозитория, на сборку уходит около 10 минут и до 8 ГБ памяти Node (`NODE_OPTIONS`):

```bash
docker build -f deploy/docs/Dockerfile --build-arg SITE_URL=https://docs.example.com -t b24-ui-docs .
docker run --rm -p 3000:3000 b24-ui-docs        # http://localhost:3000
```

Публикует образ только задача `publish` из ветки `main` и только при заданном домене; перед сборкой идёт
`pnpm audit --audit-level high` (как в `ci.yml`), сборка кэшируется в GitHub Actions cache. Права на запись
пакетов есть только у `publish`.

pnpm ставится через corepack, версия — из `packageManager` корневого `package.json`; зависимости —
`pnpm install --frozen-lockfile`. В образ попадает только `docs/.output` (Nitro уже включает нужные
`node_modules` сервера), репозитория и pnpm там нет.
