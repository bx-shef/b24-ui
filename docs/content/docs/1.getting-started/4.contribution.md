Цель проекта — дать компоненты, неотличимые от компонентов Bitrix24, чтобы улучшить пользовательский опыт и упростить разработку приложений для Bitrix24.

В основу мы взяли [Nuxt UI](https://ui.nuxt.com/). Будем рады отчётам об ошибках, pull request'ам и отзывам — они помогают сделать библиотеку лучше.

::caution
Прежде чем сообщать об ошибке или предлагать новую возможность, прочитайте [документацию](https://bitrix24.github.io/b24ui/) и просмотрите существующие [issue](https://github.com/bitrix24/b24ui/issues?q=is%3Aissue+is%3Aopen+sort%3Aupdated-desc).

Затем заполните форму: [отчёт об ошибке](https://github.com/bitrix24/b24ui/issues/new?template=bug-report.yml) или [запрос новой возможности](https://github.com/bitrix24/b24ui/issues/new?template=feature-request.yml). В форме об ошибке просят воспроизведение — от этого поля зависит, можно ли заняться отчётом.
::

## Помощь AI {#ai-assistance}

Правила участия для AI-ассистентов собраны в [`AGENTS.md`](https://github.com/bitrix24/b24ui/blob/main/AGENTS.md). Файл автоматически подхватывают все AI-агенты для кода, а в нём описаны структура компонентов, паттерны тем, соглашения о тестах и правила документации.

## Структура проекта {#project-structure}

Основные каталоги и файлы проекта Bitrix24 UI:

### Документация {#documentation}

Документация лежит в каталоге `docs` — это приложение на Nuxt, где `@nuxt/content` собирает страницы из Markdown-файлов. Как это работает, описано в [документации Nuxt Content](https://content.nuxt.com/docs/getting-started). Структура каталога:

```bash
├── app/
│   ├── assets/
│   ├── components/
│   │   └── content/
│   │       └── examples   # Компоненты-примеры для документации
│   ├── composables/
│   └── ...
├── content/
│   ├── docs/
│   │   ├── 1.getting-started
│   │   ├── 2.components   # Документация компонентов
│   │   ├── 3.composables
│   │   └── 4.typography
│   └── ...            # Посадочные страницы (index.yml, showcase.yml, templates.yml)
```

### Модуль {#module}

Код модуля лежит в каталоге `src`. Его структура:

```bash
├── plugins/
├── runtime/
│   ├── components/     # Здесь лежат все компоненты
│   │   ├── Accordion.vue
│   │   ├── Alert.vue
│   │   └── ...
│   ├── composables/
│   ├── locale/
│   ├── plugins/
│   ├── types/
│   ├── utils/
│   └── vue/
│       ├── components/
│       └── plugins/
├── theme/              # Здесь лежит тема каждого компонента
│   ├── accordion.ts    # Тема компонента Accordion
│   ├── alert.ts
│   └── ...
└── module.ts
```

## Отправка Pull Request (PR) {#submit-a-pull-request-pr}

Прежде чем начинать, проверьте, нет ли issue с описанием вашей проблемы или идеи. Если есть, оставьте в нём комментарий, что беретесь за работу.

Если нет, создайте [запрос новой возможности](https://github.com/bitrix24/b24ui/issues/new?template=feature-request.yml) и обсудите проблему или идею.

### Локальная разработка {#local-development}

Чтобы начать разработку локально, выполните шаги:

::steps{level="4"}

#### Склонируйте репозиторий `@bxshefby/b24ui-nuxt` на свой компьютер {#clone-the-bitrix24b24ui-nuxt-repository-to-your-local-machine}

```bash
git clone https://github.com/bitrix24/b24ui.git
```

#### Включите [Corepack](https://github.com/nodejs/corepack) {#enable-corepack}

```bash
corepack enable
```

#### Установите зависимости {#install-dependencies}

```bash
pnpm install
```

#### Сгенерируйте заглушки типов {#generate-type-stubs}

```bash
pnpm run dev:prepare
```

#### Запустите разработку {#start-development}

- Для работы над **документацией** в каталоге `docs` выполните:

```bash
pnpm run docs
```

- Чтобы проверить компоненты для Nuxt в **песочнице**, выполните:

```bash
pnpm run dev
```

- Чтобы проверить компоненты для Vue в **песочнице**, выполните:

```bash
pnpm run dev:vue
```

::

### Настройка IDE {#ide-setup}

Рекомендуем VSCode с [расширением ESLint](https://marketplace.visualstudio.com/items?itemName=dbaeumer.vscode-eslint). Автоисправление и форматирование при сохранении включаются так:

```json [.vscode/settings.json]
{
  "editor.codeActionsOnSave": {
    "source.fixAll": "never",
    "source.fixAll.eslint": "explicit"
  },
  "prettier.enable": false
}
```

::warning
ESLint уже настроен на форматирование кода, поэтому дублировать эту функцию в **Prettier** не нужно. Если Prettier установлен в редакторе, отключите его, чтобы избежать конфликтов.
::

### Линтинг {#linting}

Ошибки линтинга проверяет команда `lint`:

```bash
pnpm run lint # проверить ошибки линтинга
pnpm run lint:fix # исправить ошибки линтинга
```

### Проверка типов {#type-checking}

Типы проверяет TypeScript. Ошибки типов выявляет команда `typecheck`:

```bash
pnpm run typecheck
```

### Тестирование {#testing}

Перед отправкой PR запустите тесты:

```bash
pnpm run test
```

::tip
Покрытие проверяется в CI. `pnpm run test:coverage` запускает тот же набор тестов
с измерением покрытия, а
[руководство по тестированию](https://github.com/bitrix24/b24ui/blob/main/.github/contributing/testing.md#coverage)
объясняет, что эта проверка ловит, а что нет. Работает она только при полном запуске:
с `--project` или фильтром по пути она заведомо красная.
::

::tip
Чтобы обновить снимки, запустите `pnpm run test:update` — весь набор тестов, без пути.
Точечный `vitest run -u path/to/One.spec.ts` перезаписывает снимки, которые его не просили трогать,
а последующий точечный запуск их заново не отрисовывает, так что устаревшие снимки остаются зелёными.
Как это воспроизвести, описано в
[руководстве по тестированию](https://github.com/bitrix24/b24ui/blob/main/.github/contributing/testing.md#snapshot-updates).
::

### Соглашения о коммитах {#commit-conventions}

Сообщения коммитов пишутся по [Conventional Commits](https://www.conventionalcommits.org/): по ним автоматически собирается список изменений. Если вы не знакомы с форматом, прочитайте [руководство](https://www.conventionalcommits.org/en/v1.0.0/#summary).

- `fix` и `feat` — для изменений кода, которые затрагивают функциональность или логику
- `docs` — для изменений документации, `chore` — для обслуживающих задач
- `revert(Scope): …` — для отмены уже влитого изменения; заголовок пишите сами: кнопка revert на GitHub называет PR `Revert "…"`, это не conventional commit, и такой коммит молча пропадает из списка изменений
- Не начинайте строку тела коммита с токена, похожего на вызов функции: если в начале строки стоит `` `.toEqual([join(a, b)])` `` или `writeTemplates(config.root`, парсер списка изменений отклонит строку, и весь коммит будет потерян. Тот же текст в середине строки безопасен, а отступ в один пробел решает проблему

### Создание Pull Request {#making-a-pull-request}

- Следуйте [инструкциям](https://github.com/bitrix24/b24ui/blob/main/.github/PULL_REQUEST_TEMPLATE.md?plain=1), которые показываются при создании PR

- Заголовок PR должен соответствовать [Conventional Commits](https://www.conventionalcommits.org/): он пригодится после слияния кода.

- Несколько коммитов — это нормально, делать rebase и force push не нужно. При слиянии мы используем `Squash and Merge`.

- Перед отправкой PR убедитесь, что `lint`, `typecheck` и тесты проходят. Не вносите посторонних изменений.

Мы быстро посмотрим PR. Если он назначен мейнтейнеру, тот изучит его внимательно. Красный текст игнорируйте: он нужен для учёта.
